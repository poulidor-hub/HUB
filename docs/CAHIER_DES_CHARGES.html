1. Contexte et problématique

1.1 Le constat

Une organisation qui héberge ses propres applications — gestion, productivité, outils métiers — se heurte rapidement à un problème commun : chaque application réinvente sa propre gestion des utilisateurs, ses propres mots de passe, ses propres règles de droits. La multiplication des comptes fragilise la sécurité (mots de passe faibles, réutilisés, jamais révoqués) et dégrade l'expérience (multiples connexions, aucun point d'entrée unique).

1.2 Les solutions du marché et leurs limites

Les plateformes IAM (Identity & Access Management) open source de référence — Keycloak, Authentik — répondent à ce besoin, mais au prix d'une complexité notable :

  • courbe d'apprentissage élevée : concepts nombreux (realms, clients, flows, mappers), configuration délicate, documentation volumineuse ;
  • maintenance lourde : mises à jour fréquentes et parfois intrusives, migrations de configuration à surveiller, comportements implicites difficiles à auditer ;
  • empreinte disproportionnée pour un parc applicatif interne géré par une petite équipe, sur un réseau privé (LAN / VPN).

1.3 Le besoin

Un point d'entrée unique léger, autonome et lisible qui :

  1. centralise l'authentification et la gestion des utilisateurs pour l'ensemble du parc ;
  2. délègue aux applications la vérification locale des accès, sans base utilisateurs dupliquée dans chaque application ;
  3. garantit que le parc reste fonctionnel même si le point d'entrée est indisponible ;
  4. offre à l'administrateur une vision et des leviers d'exploitation (santé, journaux, sauvegardes, réseau) regroupés en un seul endroit.

Le HUB répond à ce besoin.

2. Présentation générale du HUB

2.1 Définition

Le HUB est un portail d'authentification unique (SSO) et de supervision d'un parc d'applications auto-hébergées. Il centralise les identités, émet des jetons d'accès vérifiables par chaque application, héberge le portail de lancement des applications et fournit à l'administrateur et à l'exploitant les outils d'administration du parc.

3.2 L'argument différenciant : l'indépendance des applications

Le HUB signe les jetons d'accès avec une clé privée RSA qu'il est seul à détenir. Chaque application ne possède que la clé publique correspondante : elle vérifie localement l'authenticité des jetons, mais ne peut pas en forger. Il en résulte :

  • aucune application n'héberge de base utilisateurs — la clé publique suffit ;
  • si le HUB est arrêté, les applications déjà authentifiées continuent de fonctionner pendant la durée de validité de leurs jetons ;
  • la compromission d'une application ne permet pas d'usurper les identités sur les autres.

Ce compromis — simplicité maximale côté applications, autorité centrale unique côté HUB — est le cœur du positionnement produit.

3.3 Périmètre assumé

Le HUB ne vise pas la fédération d'identités externes, la gestion d'annuaires d'entreprise ni le multi-tenant à très grande échelle. Il cible les parcs applicatifs privés (quelques dizaines d'applications et d'utilisateurs à quelques centaines) hébergés sur un réseau contrôlé, où la lisibilité et la reprise en main priment sur l'exhaustivité des fonctions.

Le HUB est déployé sur un hôte unique : ni le frontal ni l'hôte physique ne sont doublés, et aucune bascule automatique (failover) n'est prévue — ce serait contraire à l'objectif de simplicité. En contrepartie, la reprise après sinistre est traitée comme un scénario de premier ordre : snapshots chiffrés autonomes (restaurables sur une machine neuve sans dépendance à l'instance d'origine), clés de chiffrement exportées hors ligne, et procédure de restauration bare-metal semi-automatique documentée pas à pas (dépôt → secrets → stack vierge → restauration → redémarrage ; les migrations manquantes sont rejouées au démarrage, un snapshot ancien est restaurable sur une image récente). Le délai de remise en service dépend de cette procédure et de la disponibilité des clés hors ligne : il n'est pas garanti contractuellement, il est répété et outillé.

4.2 Les trois flux principaux

Connexion — l'utilisateur s'authentifie une fois sur le portail du HUB. L'API vérifie ses identifiants (et son second facteur le cas échéant) et délivre un jeton d'accès signé RS256 ainsi qu'un jeton de renouvellement.

Lancement d'une application — au clic sur une tuile du portail, le HUB génère un jeton spécifique à l'application et redirige le navigateur vers elle ; l'application vérifie le jeton avec la clé publique du HUB et ouvre la session. L'utilisateur ne retape aucun mot de passe.

Sauvegarde — chaque application pousse ses archives de sauvegarde vers le HUB avec ses propres identifiants machine-à-machine ; le HUB les stocke, les planifie, les chiffre et peut les restaurer.

4.3 Principes de déploiement

  • Tout est conteneurisé dans un unique projet Docker Compose ; le HUB peut piloter les conteneurs des applications (redémarrage, arrêt, lecture des journaux) via un accès Docker volontairement restreint.
  • Chaque application du parc est un projet Docker Compose indépendant, créé depuis un gabarit commun (voir § 9.1), avec ses propres plages de ports allouées par le HUB.
  • L'accès distant des utilisateurs passe par un serveur WireGuard intégré : seul le port VPN est exposé hors du réseau local ; tout le reste reste sur le LAN ou dans le tunnel.
  • Le HTTPS est assuré par une PKI interne : autorité de certification générée par le HUB, certificats serveur émis pour le HUB et, au besoin, pour des applications (notamment les applications relais/proxy hébergées dans le parc, qui bénéficient ainsi de certificats signés sans configuration manuelle).

5. Principes de sécurité

Couche Mécanisme mis en œuvre
Authentification Jetons JWT signés RS256, identifiant de jeton (jti) révocable, rotation des jetons de renouvellement stockés hashés avec fenêtre de grâce (re-délivrance du remplaçant pendant 60 s — fin des déconnexions multi-onglets, détection de vol préservée), identifiant utilisateur stable (UUID immuable)
Rotation des clés de signature Trousseau multi-clés (kid par empreinte RFC 7638) : rotation sans rupture (l'ancienne clé reste publiée au JWKS pendant une fenêtre de transition, 24 h par défaut), révocation d'urgence, nettoyage — endpoints d'administration et CLI dédiés ; les applications récupèrent les clés dynamiquement via JWKS (sélection par kid, cache local) — aucun redémarrage requis, ni côté HUB ni côté applications

Machine-à-machine Octroi client_credentials, secrets chiffrés au repos (Fernet), clé dédiée et obligatoire en production
Limitation de débit 5 tentatives de connexion / minute / IP sur les endpoints de saisie de mot de passe, réponses 429 avec délai indicatif. 6. Parcours « Utilisateur final »

6.1 Portail d'applications

Objectif — offrir un point d'entrée unique et lisible vers les applications du parc.

Fonctionnalités - Tableau de bord en grille des applications accessibles à l'utilisateur connecté ; - recherche instantanée par nom ; - favoris : épinglage des applications utilisées quotidiennement ; - filtres par catégorie (construits dynamiquement depuis le catalogue) et filtre atelier / production (voir § 9.8) ; - lancement en un clic : redirection transparente avec jeton d'accès (SSO).

Bénéfice — l'utilisateur ne connaît et ne mémorise qu'une seule adresse : celle du portail.

6.2 Authentification unique

Objectif — une seule identité, une seule connexion pour tout le parc.

Fonctionnalités - connexion par identifiant / mot de passe, session avec expiration et déconnexion (y compris à la fermeture de l'onglet) ; - second facteur TOTP : activation volontaire, code QR, codes de récupération ; - mot de passe oublié : réinitialisation via codes de récupération ; - demande de compte : formulaire public (activable/désactivable par l'administrateur), suivi du statut de la demande, connexion automatique après approbation ; l'administrateur notifie des administrateurs désignés et approuve ou rejette avec motif ; - changement de mot de passe forcé à la première connexion pour les comptes créés par l'administrateur avec un mot de passe par défaut.

Bénéfice — la sécurité du parc repose sur un seul point de contrôle, durci (second facteur, limitation de débit, révocation).

6.3 Profil et préférences

Objectif — laisser à chaque utilisateur la maîtrise de son environnement.

Fonctionnalités - consultation du profil et changement de mot de passe ; - préférences utilisateur (étiquettes de personnalisation) : catégories d'étiquettes définies par l'administrateur, affectées à l'utilisateur, avec accusé de consultation (fenêtre d'accueil jusqu'à validation — utile pour l'acceptation de chartes ou l'onboarding) ; - vue par l'administrateur des étiquettes de chaque utilisateur.

Bénéfice — l'administrateur communique des informations durables (chartes, rôles métier) directement dans l'environnement de chaque utilisateur.

6.4 Messagerie interne

Objectif — diffuser des informations ciblées aux utilisateurs, depuis le HUB ou depuis les applications.

Fonctionnalités - boîte de réception par utilisateur : messages lus/non lus, compteur dynamique, archivage, suppression ; - priorités : information / avertissement / urgent, avec bannière d'alerte ; - accusés : lecture, réception, clic (suivi d'engagement) ; - notifications temps réel par flux d'événements (SSE) — le message s'affiche sans rechargement ; - côté administration : envoi ciblé (un ou plusieurs destinataires) ou général (diffusion à tous), programmation différée de l'envoi, modèles de messages réutilisables, lien d'action optionnel, statistiques, export CSV, gestion complète (archivage, restauration, suppression) ; - côté applications : envoi machine-à-machine (une application notifie un utilisateur), avec synchronisation et reçus.

Bénéfice — un canal de communication officiel, traçable, qui ne dépend d'aucune messagerie externe.

7. Parcours « Administrateur »

7.1 Gestion des utilisateurs

Objectif — administrer les identités et les droits de tout le parc en un seul endroit.

Fonctionnalités - création, modification, désactivation, suppression d'utilisateurs ; - opérations en masse : création, attribution de rôles, suppression, attribution de droits applicatifs, retrait d'accès à une application ; - import CSV avec modèle téléchargeable et prévisualisation avant application ; - rôles : rôle global (administrateur / utilisateur) et rôles par application ; - profils : gabarits d'ensembles « applications + rôles » applicables en une action à des utilisateurs (avec synchronisation et détachement) ; - override de rôles de profil : ajustement individuel du niveau de droits d'une application couverte par un profil (badge « modifié », réinitialisation selon le profil) ; - identité stable : identifiant utilisateur immuable (UUID) ; renommage de l'identifiant de connexion par l'administrateur sans rupture des liaisons applicatives (jetons révoqués, identifiant OIDC préservé) ; prénom / nom éditables ; - accès atelier par utilisateur : visibilité de l'atelier d'une application accordée indépendamment du rôle sur la production — un testeur peut essayer sans accéder au service en ligne (voir § 9.8) ; - gestion des sessions : révocation immédiate des sessions d'un utilisateur (déconnexion forcée propagée en temps réel) ; - désactivation du second facteur d'un utilisateur (support) ; - recherche et pagination.

Bénéfice — l'arrivée, le changement de poste ou le départ d'un collaborateur se traitent en quelques actions, droits applicatifs compris.

7.2 Gestion des applications

Objectif — tenir le registre du parc et contrôler ce qui y entre.

Fonctionnalités - registre des applications : fiche complète (slug, nom, description, version, catégorie, icône, URLs, dépôt Git), activation/désactivation, partage en service commun ; - workflow d'approbation : toute application qui s'enregistre d'elle-même arrive en statut « en attente » ; l'administrateur approuve ou rejette avec motif ; - comptes de service (machine-à-machine) : création avec secret affiché une seule fois, régénération, périmètre d'applications attaché, secrets chiffrés au repos ; - allocation de ports et de sous-réseaux : le HUB gère un pool de plages (front / API) et de sous-réseaux Docker par application, alloue ports et sous-réseau des nouvelles applications sans collision, avec vue d'état et libération ; - catalogue GitHub : mise en cache des dépôts de l'organisation, marquage des dépôts déjà intégrés, pré-remplissage de la création d'application depuis un dépôt (avec allocation automatique des ports) ; - scanner Docker : découverte des conteneurs présents sur l'hôte, rattachement des conteneurs orphelins, resynchronisation ; - graphe de dépendances : déclaration et consultation des dépendances entre applications ; - groupes d'applications : regroupement visuel du portail (tuiles de groupes, badge, recherche par groupe), gestion administrateur (CRUD, affectation d'une application à un groupe) ; - gestion des favoris et des rôles applicatifs par utilisateur.

Bénéfice — le parc est inventorié, versionné et contrôlé ; rien n'y entre sans validation explicite.

7.3 Sauvegardes centralisées des applications

Objectif — centraliser, planifier et protéger les sauvegardes de tout le parc.

Fonctionnalités - réception des archives poussées par les applications (ZIP, somme de contrôle SHA-256) ou déclenchement par le HUB : le HUB appelle le point de sauvegarde de l'application avec un jeton machine-à-machine — c'est l'application qui construit son archive (export logique et cohérent de ses propres données) ; le HUB n'accède jamais directement à ses volumes ; - mode quiesce (par application) : pour les applications dont le stockage l'exige (bases embarquées), le HUB transmet la demande de mise au repos et l'application arrête puis redémarre elle-même son conteneur autour de son snapshot — la cohérence est obtenue sans manipulation des volumes par le HUB ; - planification cron par application (mode désactivé / manuel / planifié), exécution surveillée, statuts en cours / succès / échec, annulation d'une sauvegarde en cours ; - rétention paramétrable par application (nombre d'archives conservées) ; - export chiffré hybride RSA-OAEP + AES-256-GCM (clés dédiées distinctes des clés de signature) ou par mot de passe — format portable restaurable sur toute autre instance du HUB ; - import de sauvegardes externes : archives chiffrées (mot de passe ou clé RSA) ou ZIP brut, avec conservation optionnelle dans le registre et restauration immédiate — la migration d'une application entre instances devient un transfert de fichier ; - restauration : depuis une archive stockée ou depuis un fichier importé ; - administration globale : vue consolidée, statistiques de stockage, sauvegardes en cours, détection et purge des archives orphelines (réassociées automatiquement si l'application se réenregistre).

Bénéfice — la politique de sauvegarde du parc est définie, appliquée et vérifiée depuis une seule console.

7.4 Réseau : VPN d'accès distant intégré

Objectif — donner un accès distant sûr au parc sans exposer les services.

Fonctionnalités - serveur WireGuard intégré au projet Docker du HUB, activable/désactivable en un clic ; - configuration serveur (point de terminaison, port, sous-réseau) depuis l'interface ; - gestion des pairs : un pair = un appareil d'un utilisateur ; allocation automatique de l'adresse dans le sous-réseau VPN, activation/désactivation, suppression ; - statistiques temps réel par pair (poignée de main, présence) et du serveur ; - génération de la configuration client téléchargeable et du code QR d'enrôlement sur mobile.

Bénéfice — l'accès distant est un objet administré comme le reste du parc, sans compétence WireGuard particulière.

7.5 Certificats et HTTPS (PKI interne)

Objectif — garantir des échanges chiffrés sans dépendre d'un autorité externe.

Fonctionnalités - génération de l'autorité de certification interne au premier démarrage (clé protégée) ; - émission de certificats serveur pour le HUB (domaines et adresses déclarés, avec extensions SAN) ; - émission de certificats pour des besoins applicatifs dédiés — notamment les applications relais/proxy du parc, qui reçoivent automatiquement un certificat signé par la CA interne (routage par SNI côté frontal), sans manipulation manuelle ; - empreinte de la CA consultable pour déploiement sur les postes de travail.

Bénéfice — HTTPS partout, y compris pour les applications qui n'ont aucune compétence certificat ; suppression des avertissements navigateur sur les postes ayant importé la CA.

7.6 Paramétrage et restauration du HUB

Objectif — garder la maîtrise de la configuration et de l'état du HUB lui-même.

Fonctionnalités - paramètres à chaud (clé/valeur) : activation des demandes de compte, intégration GitHub, configuration VPN…, avec propagation temps réel aux interfaces connectées ; - adresse réseau du HUB : consultation de l'adresse effective et de sa source, changement d'adresse validé par l'administrateur avec plan de propagation aux applications (réécriture ciblée de leur configuration) et recréation des conteneurs concernés ; - snapshots système : image complète du HUB (export de la base de données, fichiers, code source des applications, sauvegardes d'applications, configuration des conteneurs), compressée puis chiffrée (RSA-OAEP + AES-256-GCM) avec la paire de clés de sauvegarde dédiée (découplée du trousseau de signature ; déchiffrement à chaîne de repli pour les archives antérieures), avec : - planification cron, rétention paramétrable, statistiques, - téléchargement de l'archive, archivage optionnel vers stockage S3, - restauration avec prévisualisation avant application, - restauration bare-metal : procédure semi-automatique sur machine neuve, les migrations manquantes étant rejouées au démarrage (un snapshot ancien est restaurable sur une image récente) ; - export / import d'environnement : export logique de la configuration (utilisateurs, applications, rôles, comptes de service) et réimport sur une autre instance, en modes création/mise à jour ; les ancres identitaires des utilisateurs (identifiants stables, liaisons OIDC) sont exportées et restaurées — une reprise après sinistre ne casse plus les liaisons applicatives.

Bénéfice — le HUB est lui-même un objet sauvegardé, restaurable et relocalisable.

7.7 Déploiement automatique des applications

Objectif — mettre en service une application depuis son dépôt Git en une action.

Fonctionnalités - déploiement complet déclenché depuis l'administration : clonage / mise à jour du dépôt (en avance rapide, sans merge), génération et injection du fichier d'environnement (slug, ports, sous-réseau, secrets préservés), construction des conteneurs, démarrage puis vérification de santé — pipeline aligné sur la voie manuelle de référence ; - configuration du dépôt Git depuis l'interface : enregistrement de l'URL du dépôt avec test de connexion immédiat — débloque mises à jour et déploiement pour les applications installées avant l'arrivée de cette intégration ; - suivi en temps réel : statut courant, étape en cours, journaux, historique des déploiements (un déploiement à la fois, persistance inter-redémarrages, annulation propre à l'arrêt du HUB) ; - lancement automatique après ajout d'une application avec URL Git, badge « non déployée » et relance manuelle pour les applications sans déploiement réussi.

Bénéfice — l'ajout d'une application au parc est automatisé de bout en bout, de son dépôt jusqu'à sa mise en service, sans manipulation manuelle d'environnement.

8. Parcours « Exploitant / Supervision »

8.1 Audit et traçabilité

Objectif — savoir qui a fait quoi, quand et d'où.

Fonctionnalités - journal d'audit : toutes les actions sensibles (connexions, gestions de comptes, approbations, sauvegardes…), filtrable par utilisateur, action, statut, adresse IP et période ; - sessions : sessions actives (avec activité temps réel), historique, révocation individuelle ; - exports CSV : journal, sessions, erreurs ; - purge automatique par durée de rétention configurable.

Bénéfice — la reconstitution d'incidents et le contrôle périodique se font en quelques clics.

8.2 Supervision des applications

Objectif — connaître en continu l'état de santé du parc.

Fonctionnalités - vérificateur de santé périodique : état de chaque application, changement d'état diffusé en temps réel aux interfaces connectées ; - cycle de vie des conteneurs : démarrage, arrêt, redémarrage d'une application depuis l'interface ; - journaux d'une application consultables directement ; - contrôle du socle d'intégration : vérification en un clic, pour chaque application, des points d'intégration au HUB (santé, authentification des utilisateurs, canal machine-à-machine, préférences, découverte de données, sauvegardes, cohérence des versions) — rapport détaillé avec score, sans aucun effet de bord ; - pilotage de l'atelier : création, mise à jour, déploiement en production et suppression de l'atelier directement depuis la vue de santé, avec suivi pas-à-pas (voir § 9.8) ; - surveillance du jeton GitHub : contrôle périodique de la validité du jeton d'accès au catalogue de dépôts, alerte immédiate des administrateurs en cas de révocation ou d'expiration (fin des dégradations silencieuses) ; - gestion des versions : comparaison version installée / version publiée sur le dépôt Git, consultation du journal des versions, des publications et de l'écart entre deux versions (aide à la décision de mise à jour).

Bénéfice — les dégradations sont vues avant d'être subies ; les mises à jour sont décidées sur information, pas au hasard.

8.3 Erreurs et alertes

Objectif — ne pas laisser une erreur silencieuse pourrir.

Fonctionnalités - journal des erreurs de l'API : capture automatique des exceptions avec pile d'appels complète ; - statistiques d'erreurs, compteur de nouvelles erreurs (badge), détail par erreur ; - acquittement global des erreurs traitées, purge ; - indicateurs (KPIs) et alertes : vue de synthèse de l'activité (connexions, utilisateurs, applications, sauvegardes) et points d'attention ; - détection automatique des boucles de requêtes : alerte sur les requêtes identiques répétées (même chemin, code HTTP, adresse IP) dans une fenêtre courte — une application qui réitère en boucle un appel en échec est signalée avant de noyer le journal.

Bénéfice — un seul endroit pour juger de la santé générale du système.

8.4 Suivi d'usage et présence (uptime)

Objectif — mesurer l'utilisation réelle de chaque application, en continu.

Fonctionnalités - segments d'usage par application : présence enregistrée par couple (session, application), avec prise en charge de l'usage parallèle de plusieurs applications (multi-onglets) sans se fermer l'une l'autre ; - présence continue par SSE : le battement de cœur des applications maintient les segments ouverts tant que l'application est utilisée ; le passage par le SSO OIDC des applications tierces est également tracé ; - clôture fidèle des segments : déconnexion, bascule d'application, expiration de session ou révocation (raisons distinctes) ; - visualisations : chronologie du jour par application (heatmap d'activité), répartition du temps par application, indicateurs de pic / moyenne / percentiles, simultanés sur longue période, avec filtres par application et par période ; les mesures portent sur l'usage production (ateliers exclus).

Bénéfice — l'exploitant mesure la charge et l'adoption réelle du parc, application par application, sans sondage intrusif.

9. Parcours « Développeur d'applications »

9.1 Gabarit d'application (template)

Objectif — créer une application du parc standardisée en quelques minutes.

Fonctionnalités - script de création d'application depuis le gabarit commun : structure projet, fichiers de configuration, ports, amorce d'enregistrement au HUB ; - conventions immédiatement opérationnelles : interface (design system partagé, thème clair/sombre automatique), API backend avec authentification déjà branchée sur le HUB, tests, sauvegarde, notifications ; - allocation automatique des ports par le HUB (plages front / API sans collision) ; - premier démarrage avec vérification de santé, puis enregistrement et approbation.

Bénéfice — le développeur démarre sur des rails : sécurité, apparence, exploitation et intégration sont déjà câblées.

9.2 Intégration machine-à-machine (M2M)

Objectif — permettre aux applications d'appeler le HUB (et d'autres applications) sans intervention humaine.

Fonctionnalités - auto-enregistrement : l'application naissante s'annonce au HUB et passe en attente d'approbation ; import en masse possible côté administration ; - ré-enregistrement auto-réparant : à la ré-inscription, le HUB retrouve ou recrée automatiquement le compte de service propriétaire de l'application (y compris après suppression en cascade) ; - octroi client_credentials : l'application obtient des jetons avec ses identifiants de compte de service (secret régénérable, chiffré au repos) ; - identité d'application fiable : chaque application ne reçoit que ses propres identifiants (jamais ceux d'une autre) ; le périmètre d'un compte de service ne publie que les applications actives, approuvées et du même contexte production/atelier ; - découverte de services : les applications déclarées « services partagés » publient leurs points d'entrée ; les autres applications les découvrent et les appellent avec leur jeton M2M ; - publication de spécification OpenAPI par chaque application (catalogue consultable, export) ; - boîte d'envoi transactionnelle (outbox) : les appels sortants différés sont persistés puis rejoués — pas de perte d'événement en cas d'indisponibilité passagère (statistiques, rejeu, nettoyage administrables) ; - rapports de dépendance : une application déclare les services qu'elle consomme et synchronise son état de conformité.

Bénéfice — les applications composent entre elles de manière sécurisée et tracée, avec résilience aux incidents réseau.

9.3 Authentification applicative (SSO)

Objectif — l'utilisateur entre dans une application sans nouveau mot de passe.

Fonctionnalités - lancement par le portail : le HUB génère un jeton propre à l'application et redirige le navigateur ; - vérification locale : l'application valide le jeton JWT avec la clé publique du HUB (point d'entrée JWKS standard) — aucune base d'utilisateurs, aucun appel au HUB à chaque requête ; - rotation des clés transparente : chaque jeton porte l'identifiant de sa clé de signature (kid) ; l'application sélectionne la bonne clé publique depuis le JWKS (cache local avec rafraîchissement) — une rotation ou une révocation côté HUB ne requiert ni redéploiement ni interruption des applications ; - introspection des jetons (RFC 7662) pour les applications qui préfèrent déléguer la vérification ; - rôles transmis dans le jeton, enrichis des rôles applicatifs.

Bénéfice — une intégration SSO qui tient en quelques lignes côté application.

9.4 Fournisseur d'identité OIDC (applications tierces)

Objectif — faire du HUB le fournisseur d'identité d'applications tierces incapables de vérifier nativement les jetons du HUB.

Fonctionnalités - point de découverte OIDC standard (/.well-known/openid-configuration) ; - flux Authorization Code (+ PKCE S256) et renouvellement — le flux le plus répandu dans les applications tierces ; - point d'information utilisateur (userinfo) ; - déconnexion par canal arrière (Back-Channel Logout) : la déconnexion au HUB révoque les jetons et notifie les applications tierces ; - administration des clients OIDC : URI de redirection en liste stricte, scopes, secrets régénérables, activation ; - auto-provisioning du client OIDC : une application du parc peut créer ou régénérer son propre client OIDC via son jeton machine-à-machine (secret affiché une seule fois) — l'intégration d'une application tierce ne requiert plus aucune intervention de l'administrateur ; - identifiant OIDC immuable : l'identifiant technique (sub) publié aux applications tierces survit au renommage de l'identifiant de connexion — les liaisons des clients existants ne se cassent jamais ; - lancement du flux depuis le tableau de bord du HUB ; - protection anti-abus sur le point d'émission des jetons (throttle sur les échecs, par client — les succès ne sont jamais pénalisés).

Bénéfice — une application tierce du marché s'intègre au parc sans compte dédupliqué et sans toucher à son code.

9.5 Déconnexion partout (SLO)

Objectif — quitter proprement toutes les applications, y compris sur un poste partagé.

Fonctionnalités - déconnexion du HUB propagée : les applications connectées sont purgées (fenêtres masquées de déconnexion) ; - détection de changement d'utilisateur sur un poste partagé : au changement de session, les sessions résiduelles de l'utilisateur précédent sont collectées et révoquées, y compris auprès des applications tierces OIDC via des relais de révocation.

Bénéfice — pas de session fantôme sur un poste utilisé par plusieurs personnes.

9.6 Poussée de sauvegardes vers le HUB

Objectif — l'application participe à la politique de sauvegarde centrale.

Fonctionnalités (côté application) - pousser une archive (ZIP + somme de contrôle) avec son jeton M2M ; - consulter ses archives, télécharger, restaurer ; - lire et appliquer sa configuration de sauvegarde (mode, cron, rétention) définie par l'administrateur — la planification est pilotée par le HUB.

Bénéfice — la sauvegarde applicative n'est pas un script oublié dans un coin : elle est configurée, exécutée et surveillée centralement.

9.7 Notifications temps réel

Objectif — informer l'utilisateur depuis une application.

Fonctionnalités - flux d'événements SSE : une connexion authentifiée par utilisateur (multi-onglets), battement de cœur 15 s (sert aussi au suivi d'activité des sessions et de la présence par application), reconnexion automatique côté client ; - diffusion d'événements de rafraîchissement (applications, utilisateurs, droits, santé, sauvegardes, messages…) — les interfaces se mettent à jour sans rechargement ; - messagerie applicative : une application envoie un message à un utilisateur via le module de messagerie du HUB (§ 6.4).

Bénéfice — les applications héritent d'un canal temps réel sans infrastructure additionnelle.

9.8 Mode atelier (workshop)

Objectif — permettre le développement et l'essai sans toucher à la production.

Fonctionnalités - toute application dont le slug porte le suffixe d'atelier est identifiée comme atelier : elle tourne dans un projet de conteneurs séparé, aux côtés de la production (qui peut être à l'arrêt pendant l'atelier), avec ports et sous-réseau dédiés ; - cycle complet piloté depuis l'interface : création (copie de la base de production), mise à jour, déploiement en production et suppression — avec suivi d'opération pas-à-pas, journal intégré et retour arrière automatique en cas d'échec (l'atelier est conservé pour diagnostic) ; - déploiement d'une branche en atelier : n'importe quelle branche du dépôt peut être déployée en atelier pour essai ; la production, elle, reste verrouillée sur la branche principale — une évolution n'y arrive qu'après validation ; - isolation stricte des clés M2M : un compte de service d'un atelier n'a accès à aucune application de production (et inversement) ; la découverte de services filtre selon le monde production/atelier — une fuite de clé ne peut plus exposer le reste du parc ; - accès par utilisateur : l'administrateur accorde la visibilité d'un atelier à un utilisateur indépendamment de son accès à la production ; les ateliers sont exclus des rôles proposés aux utilisateurs et des mesures d'usage (§ 8.4) ; - filtre tableau de bord « production / ateliers / tout ».

Bénéfice — tester une nouvelle version d'application sur une copie, sans risque de croisement avec le parc en service.

9.9 Automatisation (serveur MCP compagnon)

Objectif — piloter le HUB depuis des outils d'automatisation et assistants IA.

Fonctionnalités - un composant compagnon expose 65 outils couvrant l'ensemble de l'API : santé, gestion des applications, des utilisateurs, jetons, sauvegardes/restaurations, messages, audit, documentation, découverte de services — plus un outil d'appel arbitraire vers tout point d'API ; - authentification par compte de service M2M (aucun partage de compte humain) ; - utilisable en intégré (depuis une application du parc) ou en autonome (outils d'automatisation externes).

Bénéfice — les opérations courantes (créer un compte, déclencher une sauvegarde, acquitter des erreurs…) s'exécutent par script ou en langage naturel.

9.10 Documentation d'intégration intégrée

Objectif — que le développeur n'ait jamais à chercher la doc.

Fonctionnalités - documentation d'intégration rendue par l'API (consultable par les applications et les agents) : sections ciblées, raccourcis, version ; - journal des versions de l'API consultable programmatiquement, filtrable par version, avec écart entre deux versions — base de la vérification de compatibilité.

Bénéfice — les outils (et les agents IA) découvrent et respectent les conventions du HUB sans documentation externe à maintenir.

Annexe B — Glossaire

Terme Définition
SSO Single Sign-On — authentification unique donnant accès à plusieurs applications
JWT Jeton d'accès signé (JSON Web Token) transportant l'identité et les rôles
RS256 / JWKS Signature RSA asymétrique / point de publication standard des clés publiques
kid (Key ID) Identifiant d'une clé de signature (empreinte RFC 7638), transporté dans chaque jeton — l'application choisit la bonne clé publique depuis le JWKS
Retiring (clé) Statut transitoire d'une clé de signature remplacée : encore publiée pour la transition (24 h par défaut), puis archivée
Fenêtre de grâce Courte période où un jeton de renouvellement remplacé reste accepté — évite les déconnexions entre onglets d'une même application
M2M Machine-to-Machine — échanges entre applications sans utilisateur humain
OIDC OpenID Connect — protocole standard de fournisseur d'identité (au-dessus d'OAuth 2.0)
PKCE Protection du flux d'autorisation sur clients publics
TOTP Second facteur par code à usage unique généré par application d'authentification
SSE Server-Sent Events — flux d'événements temps réel du serveur vers le navigateur
PKI Infrastructure de clés et certificats (autorité de certification interne)
SNI Server Name Indication — routage TLS par nom de domaine demandé
WireGuard / VPN Réseau privé chiffré donnant un accès distant au parc
Quiesce Mise au repos temporaire d'un service pendant une sauvegarde
Outbox transactionnelle File persistante garantissant la livraison différée des appels sortants
Snapshot Image complète et chiffrée du HUB (à distinguer des sauvegardes d'applications)
Atelier (workshop) Copie sandbox d'une application pour développement/essais, isolée de la production
Socle d'intégration Ensemble des points d'intégration standard d'une application au HUB (santé, authentification, M2M, sauvegardes…)
MCP Protocole d'outillage pour assistants IA — expose l'API du HUB comme outils
Cron Expression de planification horaire d'une tâche récurrente
